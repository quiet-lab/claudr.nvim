## Context

Изменение добавляет к `base-plugin` ссылки на файлы, окно ввода сообщения и
диалоги агента без терминала: на диалог отвечает решение хука Claude Code, а не
клавиши в панель. Ниже — проверенные факты о Claude Code и herdr, которые не
являются поведением плагина; поведение — в требованиях `file-references`,
`message-input`, `agent-dialogs`. Решения D1–D21 заданы в `base-plugin` и здесь
не пересматриваются.

**Стенд проверок.** herdr 0.9.5 (протокол 22), Claude Code 2.1.325, модель
`haiku`, отдельные тестовые серверы без терминала. Агент запускался с ключом
`--setting-sources project`: пользовательские настройки отключены, поэтому
`agent_session` у панели оставался пустым (поле заполняет хук `SessionStart`).
Форматы Claude Code не документированы и могут измениться.

**Что отдаёт herdr.** Единственный признак диалога — `agent_status: blocked`
(в `agent get`, в снимке и событием `pane.agent_status_changed`), приходит
через 0,13–0,35 с после показа диалога. Полей с вопросом, пунктами и видом
диалога нет. `agent.prompt` в состоянии `blocked` отвечает `agent_blocked`;
при `working` принимается и встаёт в очередь.

**Хук `PermissionRequest` и диалог в панели.** Хук не подавляет диалог:
диалог показывается через 0,1–0,3 с после старта хука, состояние `blocked`
держится, пока хук ждёт. Хук и диалог — два независимых способа ответить,
побеждает первый. Хук, завершившийся без решения (код 0 и пустой вывод,
SIGTERM, SIGKILL, срок), оставляет диалог целым и полноценным. Срок задаёт
поле `timeout` записи хука, в секундах; по умолчанию 600 с (хук без ответа
получил SIGTERM через 600,06 с; при `timeout: 5` — через 5,04 с); после срока
диалог остаётся рабочим. От записи `tool_use` в транскрипте до готового
ждущего хука проходит около 0,1 с, из них запуск интерпретатора Python —
около 60 мс; запуск Neovim не измерялся.

**Что делает панель при ожидании хука.**

- Ответ цифрой в панели не даёт хуку ни сигнала, ни закрытия каналов: хук
  остаётся жить, его поздний ответ игнорируется. Завершается он выходом
  сессии (SIGTERM) либо по сроку; срок осиротевшего хука не проверялся.
- Escape в панели прерывает ход и сразу даёт хуку SIGTERM.
- `/exit` и закрытие панели дают хуку SIGTERM.
- stdin хука отдаёт EOF сразу после записи входа, закрытие stdin событием не
  служит.
- Текст, набранный в диалоге, диалог проглатывает; цифры отвечают.

**Вход и окружение хука.** Вход `PermissionRequest`: `session_id`,
`transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `hook_event_name`,
`tool_name`, `tool_input`, `permission_suggestions` (для вопроса и плана
`null`; у Bash в одном случае пустой массив); у субагента добавлены `agent_id`
и `agent_type`. Идентификатора вызова (`tool_use_id`) во входе нет. В
окружении хука есть `HERDR_PANE_ID`, `HERDR_SOCKET_PATH`, `HERDR_SESSION`,
унаследованные от панели; адреса сокета Neovim (`NVIM`) нет, так как агент
запущен из панели herdr, а не из терминала Neovim.

**Решения хука.** Вывод:
`{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{…}}}`.
Диалог при решении закрывается сам, `blocked` → `working`. В транскрипте при
любом решении появляется вложение `hook_permission_decision` (`decision`,
`toolUseID`).

| Решение | Что наблюдалось |
|---|---|
| `allow` | обычный результат инструмента |
| `allow` + `updatedInput` | выполняется изменённый вызов; модель не уведомляется, транскрипт хранит исходные аргументы |
| `allow` + `updatedPermissions` (`addRules`, `localSettings`) | правило дописано в `settings.local.json`; в живой сессии действует только при подключённом источнике настроек `local` |
| то же, `projectSettings` | правило дописано в `settings.json`, действует сразу и после перезапуска |
| то же, `addDirectories` или `setMode`, `session` | действует сразу, на диск не пишется |
| `allow` + несколько элементов `updatedPermissions` | применены все |
| `deny` + `message` | модель получает текст `message`, ход продолжается |
| `deny` + `message` + `interrupt: true` | текст до модели не доходит, ход остановлен как при Escape |

Документация: формат `updatedPermissions` тот же, что у `permission_suggestions`,
хук может вернуть полученный элемент; `message` — только для `deny`,
`updatedInput` и `updatedPermissions` — только для `allow`; правила отказа
проверяются и после `allow` хука.

**Вопрос и план решением хука.** Ответ на вопрос — `allow` с `updatedInput`,
содержащим `questions` как пришли и `answers` вида «текст вопроса → метка»;
у множественного выбора метки через запятую с пробелом
(`"Cheese, Olives"`). Модель получает тот же `tool_result`, что при ответе в
панели. Голый `allow` без `updatedInput` ничего не делает, диалог остаётся.
Свободный ответ в панели записывается в `answers` самим текстом с переводами
строк. План: `allow` с `updatedInput`, равным `tool_input`, даёт «User has
approved your plan», режим сменился на `default`; `deny` с `message` даёт
`tool_result` с ошибкой и текстом, модель дописывает план и вызывает
`ExitPlanMode` снова, режим остаётся `plan`.

**Пункты диалога разрешения.** Первый пункт экрана всегда «Yes», последний —
отказ; между ними пункты, порождённые `tool_name`, режимом и элементами
`permission_suggestions`, но не позиционно: у Bash есть пункт «switch to auto
mode» без элемента, `setMode` у Bash в предложениях есть, а на экране его нет;
два элемента Write вне каталога (`setMode`, `addDirectories`) слиты в один
пункт; элемент `addRules` с несколькими правилами — один пункт, и в нём
перечислены все правила команды, включая уже разрешённые; массив может быть
пустым. Встречались элементы `addDirectories` (`session`), `setMode`
(`session`), `addRules` (`localSettings`, для Read и MCP — `session`). Элемент
`addDirectories` у Bash подтверждения команд не отменяет. Пункт «switch to
auto mode» элемента не имеет, хуком он недоступен.

**Одновременные запросы.** Два вызова Bash в одном ходе идут последовательно,
ждёт один хук. Два параллельных `Read` вне проекта дают два ждущих хука при
одном диалоге на экране; порядок `PreToolUse` и `PermissionRequest` у них не
совпал. Хук субагента и хук главной сессии ждут одновременно, оба решения
исполняются. Транскрипт субагента — `<сессия>/subagents/agent-<agent_id>.jsonl`.

**Транскрипт.** Запись `assistant` с `tool_use` для Bash есть до ответа и без
хуков; для вопроса и плана до ответа наблюдалась только в сессиях с хуками
`PreToolUse` и `PermissionRequest`. Закрытие вызова — запись `user` с
`tool_result`. Отказ в панели (цифра пункта «No», Escape) даёт `tool_result`
с `is_error` и запись «[Request interrupted by user for tool use]»; `deny` с
`message` второй записи не даёт.

**Сообщение агенту.** Многострочный текст доходит одним сообщением: herdr
отправляет его вставкой (bracketed paste), запись транскрипта обёрнута в
`<pasted_content id=…>`. Начало с `/` Claude Code разбирает как команду, с
`!` — переводит поле в режим оболочки; начало с пробела перед `/` — обычное
сообщение. Порог обёртки не выяснялся.

## Goals / Non-Goals

**Goals:**

- Путь под курсором в любом буфере с содержимым Claude Code открывается
  предпросмотром и переходом.
- Сообщение агенту набирается как обычный текст в Neovim.
- На диалог агента (вопрос, множественный выбор, несколько вопросов,
  разрешение со всеми пунктами, подтверждение плана) отвечает Neovim решением
  хука, без клавиш в панель; без Neovim и без хука остаётся обычный диалог.

**Non-Goals:**

- Разбор экрана панели; клавиши в панель для ответа на диалог.
- Пункт «перейти в режим auto» — хуком недоступен, остаётся терминалу.
- Диалоги, не приходящие через `PermissionRequest` (доверие каталогу, MCP
  elicitation): остаются терминалу.
- Хранение черновиков между запусками Neovim.

## Decisions

Решения D22, D23, D30, D32, D33 и часть D24, D27, D29 приняты пользователем;
остальные предложены при пересмотре под решение хука и утверждаются
пользователем вместе с дельтами. Нумерация продолжает `base-plugin`.

### D22. Содержимое диалога и ответ — через хук `PermissionRequest`

В условиях, когда herdr отдаёт только состояние `blocked`, транскрипт не
гарантирует запись вопроса и плана до ответа, а хук получает `tool_input` до
показа диалога и может вернуть решение, выбрано брать структуру диалога от
хука, поставляемого с плагином, и отвечать на все три вида диалогов (запрос
разрешения, вопрос, план) его решением, чтобы буфер строился из разобранных
данных, а ответ не зависел от нумерации пунктов и внешнего вида экрана, ценой
установки хука в Claude Code (сессия без хука остаётся на терминале). Принято
пользователем.

### D23. Разбор экрана не делается

В условиях, когда подвал, нумерация и строки вкладок меняются между
диалогами, выбрано не разбирать экран панели ни в каком случае и при
отсутствии запроса предлагать терминал, чтобы изменение оформления Claude Code
не ломало плагин незаметно, ценой отказа от диалогов без хука. Принято
пользователем.

### D24. Хук поставляется плагином Claude Code, событие одно

В условиях, когда хук должен быть установлен у пользователя, а ставить его
вручную в настройки неудобно, выбрано поставлять плагин Claude Code в
каталоге `claude-plugin/` (манифест, описание хука, сценарий) и описать
установку в `docs/`, чтобы хук обновлялся вместе с плагином. Принято
пользователем в части поставки. Состав — на утверждение с дельтой: единственное
событие `PermissionRequest` для всех инструментов (оно приходит для вопроса и
плана; `PreToolUse` не нужен, так как идентификатор вызова берётся из
транскрипта, D34, а хук перед каждым вызовом инструмента запускал бы процесс
впустую). Сценарий — Lua-файл, который запускает `nvim --clean -l`: Neovim у
пользователя уже есть, `jq` и оболочка не нужны. Отвергнуто: `jq` с оболочкой —
лишняя зависимость.

### D25. Канал хука и Neovim — Unix-сокет по известному пути

В условиях, когда хук запускает Claude Code, адреса сокета Neovim в окружении
хука нет, а таймеры, опрос и файлы-посредники запрещены, выбрано слушать
Unix-сокет `<каталог времени выполнения>/claudr/<pid>.sock` в плагине
(`vim.uv.new_pipe`, как в D13), а хуку при запуске соединяться, передавать вход
одной строкой JSON и ждать решения чтением сокета, чтобы обмен шёл по событиям
соединения и без файлов, ценой того, что запрос, начатый до запуска Neovim или
при перезапуске Neovim, виден только в панели. Каталог — `XDG_RUNTIME_DIR`
(заменяется переменной окружения для тестов), доступ только владельцу. Формат
обмена — строки JSON: от хука `request` (`version`, вход хука целиком,
`HERDR_PANE_ID`, `HERDR_SOCKET_PATH`), от плагина `decision` (готовый вывод
хука) либо закрытие соединения, от хука `answered` (см. D26). Решение
собирается плагином, хук печатает его как есть и форматов не знает. Без
слушателя хук завершается сразу с кодом 0 и пустым выводом, ошибки хука
диалогу не мешают. Файлов-посредников нет. На утверждение с дельтой.

### D26. Несколько экземпляров Neovim — хук соединяется со всеми

В условиях, когда одновременно могут работать несколько Neovim (в том числе
к разным серверам herdr), выбрано держать у каждого экземпляра свой сокет в
общем каталоге, хуку соединяться со всеми доступными, первому полученному
решению дать победить, остальным отправить «отвечено» и закрыть, чтобы не
вводить выбор ведущего экземпляра и блокировки, ценой того, что экземпляр,
решение которого проиграло, узнаёт об этом после отправки. Экземпляр
принимает запрос, только если `HERDR_SOCKET_PATH` запроса совпадает с его
сервером и панель известна дереву; иначе закрывает соединение без ответа,
хук такое соединение не считает. Сокеты умерших экземпляров убирает следующий
запуск плагина; хук чужих сокетов не удаляет. Отвергнут единственный
слушатель: второй экземпляр оставался бы без запросов, а выбор владельца
сокета потребовал бы блокировки. На утверждение с дельтой.

### D27. Закрытие запроса — по событиям, диалог панели не трогается

В условиях, когда ответ может быть дан в панели или другим клиентом, а хук о
таком ответе не узнаёт, выбрано считать запрос закрытым по записи результата
вызова в транскрипте (`tool_result` для идентификатора вызова), по закрытию
соединения хуком (SIGTERM при Escape, выходе сессии, истёкшем сроке — хук
закрывает соединения) и по команде «передать диалог терминалу» (плагин
закрывает соединение без решения), чтобы буфер диалога закрывался или
помечался отвеченным при любом источнике ответа, а диалог в панели оставался
рабочим всё время, ценой того, что осиротевший хук живёт, пока плагин не
увидит результат вызова. Ответ в панели хук не прерывает; плагин сам закрывает
его соединение, и хук завершается без решения. Принято пользователем в части
транскрипта; остальное — на утверждение с дельтой.

### D28. Решение собирается одним модулем по виду запроса

В условиях, когда формы решения различаются по видам диалога, а формат вывода
хука зависит от версии Claude Code, выбрано собирать решение в одном модуле по
таблице вида запроса, чтобы расхождение с новой версией правилось в одном
месте, ценой отказа от непроверенных форм (см. Open Questions). На
утверждение с дельтой.

| Запрос и действие | Решение хука |
|---|---|
| разрешение, «разрешить один раз» | `allow` |
| разрешение, пункт элемента | `allow` + `updatedPermissions`: этот элемент без изменений |
| вопрос, ответ | `allow` + `updatedInput`: `questions` как пришли и `answers` |
| план, «подтвердить» | `allow` + `updatedInput`: исходный `tool_input` |
| любой вид, «отказать» | `deny` |
| любой вид, «отказать с пояснением» | `deny` + `message` из окна ввода |
| любой вид, «отказать и прервать» | `deny` + `interrupt: true` |

Ответ на вопрос: одиночный выбор — метка пункта; множественный — метки
отмеченных через запятую с пробелом в порядке пунктов; свой ответ — текст как
есть; несколько вопросов — один `allow` со всеми ответами по текстам вопросов.

### D29. Разрешение — все пункты, кроме перехода в режим auto

В условиях, когда пользователь хочет видеть «разрешать всегда» и подобные
пункты, а хук отвечает элементом `permission_suggestions`, выбрано показывать
по пункту на каждый элемент массива (в порядке массива) вместе с
«разрешить один раз», «отказать», «отказать с пояснением» и «отказать и
прервать», а подпись пункта собирать из данных элемента: вид правила,
инструмент и содержимое правила (без содержимого — любой вызов инструмента),
каталоги, режим и место сохранения (сессия, местные настройки проекта,
настройки проекта, пользовательские настройки), чтобы пользователь видел,
что именно и куда запишет пункт, ценой того, что подписи на русском
расходятся с английским текстом экрана, а слитые на экране элементы (Write
вне каталога) в буфере разделены. Пункт «перейти в режим auto» экрана
элемента не имеет и хуком недоступен: буфер говорит об этом прямо, он
остаётся терминалу. Принято пользователем; сбор подписей — на утверждение с
дельтой.

### D30. Окно ввода общее для сообщений, свободного ответа и пояснений

В условиях, когда сообщение агенту, свободный ответ на вопрос и пояснение к
отказу — один и тот же набор текста, выбрано использовать одно всплывающее
окно с обычным редактированием, отправкой сохранением (`:w`), Shift+Enter или
Shift+Space и разной целью отправки (`agent.prompt`, ответ вопроса, `message`
отказа), чтобы не плодить интерфейсы. Принято пользователем. Черновик
(закрытие без отправки сохраняет текст до следующего открытия для той же
сессии; в памяти Neovim) — на утверждение с дельтой. Shift+Enter и Shift+Space
различимы только терминалом с расширенным протоколом клавиатуры; `:w`
работает всегда.

### D31. Начало сообщения с `/` или `!`

В условиях, когда пользователь мог написать команду Claude Code намеренно, а
вставляемый текст может начинаться с `/` или `!` случайно, выбрано
отправлять текст как есть и сообщать об этом перед отправкой, предоставив
настройку защиты ведущим пробелом, чтобы не лишать пользователя команд,
ценой возможной случайной команды. На утверждение с дельтой. Вариант:
защита по умолчанию включена — безопаснее для вставки, но команды тогда
набираются с обходом. Пробел перед `!` не проверен.

### D32. Ссылки на файлы — общий разбор и клавиши только в буферах плагина

В условиях, когда содержимое Claude Code показывают шесть видов буферов,
выбрано определять ссылку одним модулем (виды `файл`, `файл:строка`,
`файл:строка:столбец`; относительный путь — от рабочего каталога сессии
владельца буфера: `cwd` панели, для субагента и фоновой команды — `cwd`
панели владельца, для диалога из истории — каталог проекта сессии, для темы
— каталог проекта темы; несуществующий путь и каталог ссылкой не считаются)
и назначать `K` (предпросмотр на строке в плавающем окне, только чтение,
фокус на месте, закрытие по движению курсора и Escape) и `gd` (открытие в
окне редактирования на строке и столбце) только в этих буферах, чтобы
остальные буферы не затрагивались, ценой переназначения настройкой. Вне
ссылки клавиши работают как обычно. Принято пользователем.

### D33. Без самовольной смены окна

В условиях, когда агент переходит в ожидание, пока пользователь работает в
другом окне, выбрано только сообщать об этом и о команде открытия диалога,
не меняя окно и фокус. Принято пользователем.

### D34. Перечень ждущих запросов и сопоставление с вызовом

В условиях, когда во входе `PermissionRequest` нет идентификатора вызова, а
ждать одновременно могут несколько запросов (параллельные вызовы, субагент
вместе с главной сессией), выбрано вести в плагине перечень ждущих запросов
по соединениям, ключом сопоставления считать сессию, `agent_id` (если есть),
инструмент и равный по значению `tool_input`, а идентификатор вызова брать из
транскрипта (для субагента — из его транскрипта): запись `tool_use` того же
инструмента с равным входом, без результата и не занятая другим запросом;
если записи нет, ждать её по событию записи в файл. Порядок событий хуков
ключом не служит: у параллельных `Read` он не совпал. Узел дерева показывает
число своих запросов, узел панели — и запросов её субагентов; буфер
открывается на выбранный запрос. Привязка к узлу — `HERDR_PANE_ID`
окружения хука (субагент наследует его от сессии) и `agent_id` входа;
`session_id` входа определяет транскрипт (D15). Ценой решения: одинаковые
вызовы в одном ходе неразличимы (решение любому из них равнозначно по
входу), они сопоставляются по порядку записей, а подтверждает верный вызов
вложение `hook_permission_decision`. Отвергнуто: хук `PreToolUse` с тем же
ключом — запускал бы процесс перед каждым вызовом инструмента. На
утверждение с дельтой.

### D35. Срок ожидания хука задаёт Claude Code

В условиях, когда хук ждёт решения пользователя неопределённо долго, а Claude
Code по умолчанию завершает хук через 600 с, выбрано задать в записи хука
плагина Claude Code `timeout` в сутки (86400 с), чтобы запрос переживал
обычный перерыв пользователя, ценой того, что по истечении срока хук
завершается, плагин по закрытию соединения помечает запрос «ответ в панели», а
диалог панели остаётся рабочим. Срок — свойство процесса хука, которым владеет
Claude Code; в плагине Neovim таймера нет, закрытие по сроку приходит событием
закрытия соединения, поэтому правило «без таймеров и опроса» не нарушено. На
утверждение с дельтой.

## Что уточняет base-plugin

Уточнения оформлены дельтами `## MODIFIED Requirements` этого изменения
(`specs/<возможность>/spec.md`):

- `code-questions`: «Ссылки на код в ответе» — клавиши и предпросмотр задаёт
  `file-references`, переход соответствует `gd`; «Ответ по мере генерации» —
  выход из Neovim не останавливает отвечающий процесс.
- `messaging`: «Сообщение агенту» — ввод окном `message-input`, а не
  `vim.ui.input`; «Агент в состоянии без приёма сообщений» — буфер диалога
  при ждущем запросе, иначе предложение подключения с вводом, без клавиш
  (решение D11 уточняется так же). Требование «Клавиши агенту» не меняется:
  `pane.send_keys` остаётся только там.
- `node-view`: «Панель — ввод отдельной командой» — запасной путь для сессий без
  хука и диалогов вне хука.
- `agent-tree`: «Состояние панели с агентом» — число ждущих запросов.
- `claude-code-data`: «Единый модуль чтения данных Claude Code» — разбор входа
  хука и вложения `hook_permission_decision`.

## Risks / Trade-offs

- Формат решения хука зависит от версии Claude Code (имена полей, `answers`,
  `updatedPermissions`) → решение собирается одним модулем, образцы в тестах,
  живая проверка до включения. При несовпадении решение не принимается
  (голый `allow` у вопроса ничего не делает), диалог в панели остаётся
  рабочим, буфер показывает «решение отправлено» без подтверждения
  `hook_permission_decision` и результата вызова, а панель отвечает как
  обычно.
- Хук не установлен или не сработал, запрос принят чужим экземпляром или
  закрыт по сроку → диалог остаётся в панели (требование «Диалог без запроса
  или нераспознанный»).
- Запрос, начатый до запуска Neovim, и запрос при перезапуске Neovim виден
  только в панели: хук соединяется один раз при старте и не ждёт слушателя.
- Ответ в панели хук не прерывает → осиротевший хук живёт, пока плагин не
  увидит результат вызова в транскрипте; пока идентификатор вызова не найден,
  такой запрос не закрывается по транскрипту (закроют выход сессии или срок).
- Одинаковые вызовы в одном ходе неразличимы (D34); два вопроса одного
  вызова с одинаковым текстом неразличимы в `answers`.
- Хуки других плагинов на тот же вызов: побеждает первое решение; запрос
  закрывается по результату вызова. Сочетание не проверялось.
- Правила отказа Claude Code проверяются и после `allow` хука: запрос,
  разрешённый в буфере, может быть отклонён правилом; об этом говорит
  результат вызова.
- Пункты с `userSettings` пишут в пользовательские настройки; подпись
  называет место, пункт не скрывается.
- Подписи элементов собираются плагином, а не берутся с экрана: расхождение
  с формулировками экрана допустимо, смысл выводится из полей элемента.

## Open Questions

Все закрываются живой проверкой этапа 6 (`tasks.md`, 6.2) на отдельном
тестовом сервере; до закрытия перечисленные формы опираются на документацию
Claude Code, а не на наблюдение, расхождение правит модуль решений (D28) и
дельту.

1. Форма `answers` у множественного выбора при метке с запятой, у свободного
   текста через решение хука (наблюдался только ответ в панели) и у
   нескольких вопросов вперемешку со свободным ответом.
2. Что получает модель при `deny` без `message` и при `deny` с
   `interrupt: true` без `message`; `deny` с `interrupt` для вопроса и плана
   не проверялся.
3. Режим после подтверждения плана: наблюдался только `default`; какой
   элемент `updatedPermissions` (`setMode`) даёт «auto» и «принимать
   правки».
4. Применение элементов с `userSettings`, `replaceRules`, `removeRules`,
   `removeDirectories` (проверка — в отдельном пустом каталоге настроек Claude
   Code, не в пользовательском).
5. Запись `tool_use` вопроса и плана до ответа при установленном только
   хуке `PermissionRequest` (наблюдалась при двух хуках); если записи нет,
   идентификатор вызова придётся брать другим способом (вернуть `PreToolUse`).
6. Верхний предел `timeout` (принимается ли 86400 без усечения) и срок
   осиротевшего хука (убивается ли он по `timeout` после ответа в панели).
7. Гонка: ответ в панели и решение хука в одну долю секунды.
