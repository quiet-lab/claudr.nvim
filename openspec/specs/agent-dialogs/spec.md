# agent-dialogs Specification

## Purpose
Ответы на диалоги Claude Code (вопрос, запрос разрешения, подтверждение плана) из буфера Neovim, а не из терминала панели: решение отдаёт хук `PermissionRequest`.

## Requirements

### Requirement: Плагин Claude Code с хуком
Вместе с claudr.nvim MUST поставляться плагин Claude Code (каталог `claude-plugin/`) с одним хуком на событие `PermissionRequest` для всех инструментов, включая `AskUserQuestion` и `ExitPlanMode`. В записи хука MUST быть задан `timeout` не меньше суток. Других событий хук MUST NOT использовать.

#### Scenario: Описание хуков
- **WHEN** читается описание хуков плагина Claude Code
- **THEN** в нём одна запись `PermissionRequest` без ограничения по инструменту, `timeout` не меньше 86400 секунд, других событий нет

### Requirement: Сокет плагина Neovim
Каждый экземпляр Neovim с плагином MUST слушать Unix-сокет `<каталог времени выполнения>/claudr/<pid>.sock` и принимать соединения по событиям. Каталог — `XDG_RUNTIME_DIR`, заменяется переменной окружения; доступ к нему MUST быть только у владельца. Сокет MUST удаляться при выходе; при запуске MUST удаляться сокеты, к которым нельзя подключиться.

#### Scenario: Запуск и выход
- **WHEN** Neovim запускается, затем завершается
- **THEN** сокет с pid этого экземпляра появляется в каталоге и исчезает при выходе

#### Scenario: Сокет умершего экземпляра
- **WHEN** при запуске в каталоге лежит сокет, к которому подключиться нельзя
- **THEN** плагин удаляет его, сокеты живых экземпляров остаются

### Requirement: Запрос хука к Neovim
При запуске хук MUST подключиться ко всем доступным сокетам каталога и передать каждому одной строкой JSON запрос: вход хука целиком, `HERDR_PANE_ID` и `HERDR_SOCKET_PATH` окружения. Затем хук MUST ждать решения чтением сокетов. Если подключиться не к чему, хук MUST завершиться кодом 0 без вывода.

#### Scenario: Слушателя нет
- **WHEN** в каталоге нет сокетов или подключение ко всем отказано
- **THEN** хук сразу завершается с кодом 0, stdout пуст

#### Scenario: Два экземпляра
- **WHEN** слушают два экземпляра Neovim
- **THEN** оба получают одинаковый запрос с входом хука, хук ждёт

### Requirement: Первое решение побеждает
Первое полученное хуком решение MUST печататься в stdout как вывод `PermissionRequest`, после чего хук завершается кодом 0. Остальным соединениям хук MUST отправить сообщение «отвечено» и закрыть их; плагин MUST закрыть такой запрос и сообщить, что ответ принят другим экземпляром.

#### Scenario: Ответ из первого экземпляра
- **WHEN** два экземпляра получили запрос, первый присылает решение
- **THEN** stdout хука содержит это решение, второй экземпляр получает «отвечено» и закрывает запрос

### Requirement: Хук не мешает диалогу
Хук MUST NOT печатать в stdout ничего, кроме решения, и MUST NOT писать файлы. Закрытие всех соединений без решения, ошибка соединения или разбора MUST завершать хук кодом 0 без вывода. По SIGTERM хук MUST закрыть соединения и завершиться кодом 0. Диалог Claude Code при любом исходе остаётся рабочим.

#### Scenario: Соединения закрыты
- **WHEN** все экземпляры закрывают соединения, не прислав решения
- **THEN** хук завершается с кодом 0, stdout пуст

#### Scenario: Сигнал завершения
- **WHEN** ждущий хук получает SIGTERM
- **THEN** соединения закрыты, код выхода 0, stdout пуст

### Requirement: Строка агента панели
Строкой агента панели MUST считаться строка прочего агента вкладки, если панель не агент вкладки (`agent-tree`, «Агент вкладки»), иначе строка вкладки, а при скрытой единственной вкладке — строка workspace.

#### Scenario: Запрос агента вкладки
- **WHEN** приходит запрос без `agent_id` от панели агента вкладки `w1:t1`, у workspace две вкладки
- **THEN** запрос привязан к строке `w1:t1`

### Requirement: Приём запроса и привязка к узлу
Плагин MUST принимать запрос, только если `HERDR_SOCKET_PATH` запроса совпадает с сервером herdr плагина, а `HERDR_PANE_ID` — панель из снимка этого сервера; иначе MUST закрыть соединение без ответа. Запрос с `agent_id` MUST привязываться к узлу этого субагента, если он есть в дереве, иначе к строке агента панели; запрос без `agent_id` — к строке агента панели.

#### Scenario: Чужой сервер
- **WHEN** `HERDR_SOCKET_PATH` запроса указывает на другой сервер herdr
- **THEN** плагин закрывает соединение, запрос в перечень не попадает

#### Scenario: Запрос субагента
- **WHEN** запрос содержит `agent_id` субагента, узел которого есть под вкладкой
- **THEN** запрос привязан к узлу субагента

#### Scenario: Запрос агента вкладки
- **WHEN** запрос без `agent_id` пришёл от панели `w1:p1` вкладки `w1:t2`
- **THEN** запрос привязан к строке `w1:t2`

### Requirement: Перечень ждущих запросов
Плагин MUST вести перечень ждущих запросов: несколько могут ждать одновременно (параллельные вызовы, субагент вместе с главной сессией). Ключ сопоставления — сессия, `agent_id` (если есть), инструмент и равный по значению `tool_input` (у `ExitPlanMode` — без поля `plan`). Узел MUST показывать число своих ждущих запросов, строка агента — и запросов его субагентов. Запрос в состоянии «решение отправлено», чей хук закрыл соединение, MUST NOT считаться ждущим.

#### Scenario: Два параллельных вызова
- **WHEN** сессия присылает два запроса `Read` с разными `file_path`
- **THEN** строка вкладки показывает два запроса, у каждого свой ключ

#### Scenario: Субагент и главная сессия
- **WHEN** ждут запрос субагента и запрос главной сессии той же панели
- **THEN** узел субагента показывает один, строка вкладки — два

#### Scenario: Решение отправлено, хук завершился
- **WHEN** решение по запросу отправлено, хук закрыл соединение, подтверждения в транскрипте ещё нет
- **THEN** узел не считает запрос ждущим, выбор запроса его не предлагает, буфер показывает «решение отправлено»

### Requirement: Идентификатор вызова
Вход `PermissionRequest` не несёт идентификатора вызова: плагин MUST находить его в транскрипте как запись `tool_use` того же инструмента с равным `tool_input` (у `ExitPlanMode` — без поля `plan`, которое Claude Code подставляет из файла), без результата и не занятую другим запросом (для субагента — в его транскрипте). Если записи ещё нет, плагин MUST ждать её по событию записи в файл. Неразличимые вызовы MAY сопоставляться по порядку записей.

#### Scenario: Запись уже есть
- **WHEN** в транскрипте есть `tool_use` `Bash` с той же командой и без результата
- **THEN** запросу назначен его идентификатор вызова

#### Scenario: Запись позже запроса
- **WHEN** запрос получен, а `tool_use` дописывается в транскрипт позже
- **THEN** идентификатор назначается при дописывании, без опроса

#### Scenario: План правится в том же сообщении
- **WHEN** модель в одном сообщении переписала файл плана и вызвала `ExitPlanMode`, текст `plan` во входе хука отличается от записи `tool_use`
- **THEN** запросу назначен идентификатор вызова этой записи

### Requirement: Закрытие по результату вызова
Запрос MUST закрываться, когда в транскрипте появляется результат его вызова (`tool_result`, в том числе с ошибкой). Плагин MUST закрыть соединение (хук завершится без решения) и закрыть буфер диалога либо пометить его отвеченным в панели или другим клиентом.

#### Scenario: Ответ в панели
- **WHEN** запрос ждёт, пользователь отвечает цифрой в панели, в транскрипте появляется `tool_result`
- **THEN** соединение закрыто, буфер диалога помечен отвеченным в панели или закрыт

### Requirement: Диалог в панели не затрагивается
Показ запроса в Neovim MUST NOT менять диалог в панели: он остаётся на экране и рабочим, пока нет решения. Плагин MUST NOT отправлять в панель клавиши и текст ради ответа на диалог и MUST NOT читать экран панели.

#### Scenario: Запрос ждёт
- **WHEN** запрос ждёт решения в Neovim
- **THEN** к серверу herdr нет вызовов `pane.send_keys`, `pane.send_text` и `pane.read` по этому диалогу

### Requirement: Закрытие запроса хуком
Если соединение закрыл хук (Escape в панели, истёкший срок хука, выход сессии), плагин MUST закрыть запрос и пометить буфер «закрыт хуком, ответ в панели»; решение по такому запросу MUST NOT отправляться.

#### Scenario: Срок хука истёк
- **WHEN** хук завершился по сроку и соединение закрыто
- **THEN** запрос закрыт, буфер помечен «ответ в панели», диалог панели не тронут

### Requirement: Передача диалога терминалу
Команда буфера «передать терминалу» MUST закрывать соединение запроса без решения, закрывать буфер и предлагать подключение с вводом (`node-view`). Диалог остаётся в панели обычным.

#### Scenario: Передача
- **WHEN** пользователь вызывает команду «передать терминалу»
- **THEN** соединение закрыто без решения, хук завершён кодом 0 без вывода, предложено подключение с вводом

### Requirement: Разбор входа хука в claude-code-data
Вход хука MUST разбираться тем же модулем, что транскрипты. Модуль MUST возвращать запись «запрос»: вид (`question` для `AskUserQuestion`, `plan` для `ExitPlanMode`, иначе `permission`), вопросы с пунктами и `multiSelect`, текст плана, содержимое разрешения, элементы `permission_suggestions` (поле может быть `null` или пустым). Неизвестные поля и инструменты MUST NOT вызывать ошибку.

#### Scenario: Вопрос с вариантами
- **WHEN** вход содержит `AskUserQuestion` с одним вопросом и тремя пунктами
- **THEN** запрос вида `question` с тремя пунктами и подписями

#### Scenario: Пустые предложения
- **WHEN** `permission_suggestions` равно `null`
- **THEN** у запроса нет элементов, ошибки нет

### Requirement: Буфер диалога
Запрос MUST показываться обычным буфером только для чтения с навигацией Vim, курсор на первом пункте, Enter на пункте — ответ. Буфер MUST открываться одной командой из узла дерева и из вида панели; при нескольких запросах — на выбранный, с командой перехода к следующему. Окно и фокус плагин MUST NOT менять сам.

#### Scenario: Открытие с узла
- **WHEN** пользователь вызывает команду диалога на узле с запросом
- **THEN** открывается буфер только для чтения, курсор на первом пункте

#### Scenario: Запроса нет
- **WHEN** команда вызвана на узле без ждущего запроса
- **THEN** плагин сообщает, что ждущего запроса нет

### Requirement: Пункты запроса разрешения
Буфер разрешения MUST показывать инструмент и содержимое (команда; файл и текст; иначе `tool_input`) и пункты по порядку: «разрешить один раз»; по пункту на каждый элемент `permission_suggestions` в порядке массива; «отказать»; «отказать с пояснением»; «отказать и прервать». Пункт «перейти в режим auto» плагин не предлагает (элемента `permission_suggestions` для него нет): буфер MUST сообщать, что он остаётся терминалу.

#### Scenario: Два элемента
- **WHEN** `permission_suggestions` содержит два элемента
- **THEN** между «разрешить один раз» и «отказать» два пункта в порядке массива

#### Scenario: Пустые предложения
- **WHEN** элементов нет
- **THEN** пунктов, кроме разрешения один раз и отказов, нет

### Requirement: Подписи пунктов из данных хука
Подпись пункта элемента MUST собираться из его данных: вид (`addRules`, `addDirectories`, `setMode`), инструмент и содержимое правила (без содержимого — любой вызов инструмента), каталоги, режим и место сохранения: `session` — сессия, `localSettings` — местные настройки проекта, `projectSettings` — настройки проекта, `userSettings` — пользовательские настройки. Элемент неизвестного вида показывается с видом и местом.

#### Scenario: Правило в местные настройки
- **WHEN** элемент — `addRules` с `Bash` и `git init *` в `localSettings`
- **THEN** подпись называет правило `Bash` с `git init *` и «местные настройки проекта»

#### Scenario: Каталог на сессию
- **WHEN** элемент — `addDirectories` с одним каталогом в `session`
- **THEN** подпись называет каталог и «сессия»

### Requirement: Решения по запросу разрешения
«Разрешить один раз» MUST давать решение `allow`. Пункт элемента MUST давать `allow` с `updatedPermissions`, содержащим этот элемент без изменений. «Отказать» MUST давать `deny`; «отказать с пояснением» — `deny` с `message` из окна ввода; «отказать и прервать» — `deny` с `interrupt: true`. Решение собирается одним модулем.

#### Scenario: Пункт элемента
- **WHEN** пользователь выбирает пункт второго элемента `permission_suggestions`
- **THEN** плагин присылает хуку `allow` с `updatedPermissions` из одного этого элемента

#### Scenario: Отказ с пояснением
- **WHEN** пользователь отказывает и отправляет из окна ввода текст
- **THEN** решение — `deny` с `message`, равным тексту

### Requirement: Ответ на вопрос с одним выбором
Enter на пункте вопроса с одним выбором MUST давать `allow` с `updatedInput`: исходные `questions` без изменений и `answers` — объект «текст вопроса → метка пункта».

#### Scenario: Второй пункт
- **WHEN** пользователь выбирает `Green` в вопросе `Which color?`
- **THEN** решение — `allow`, `updatedInput.answers` равно `{"Which color?": "Green"}`, `questions` как во входе

### Requirement: Свой ответ на вопрос
Пункт «свой ответ» после перечня пунктов, в вопросе с одним выбором и с `multiSelect`, MUST открывать окно ввода (`message-input`); отправленный текст MUST попадать в `answers` как значение ответа на этот вопрос без изменений, с переводами строк. В множественном выборе текст заменяет отметки.

#### Scenario: Текст из двух строк
- **WHEN** пользователь отправляет из окна ввода текст из двух строк
- **THEN** значение ответа на вопрос в `answers` — этот текст с переводом строки

#### Scenario: Свой ответ в множественном выборе
- **WHEN** в вопросе с `multiSelect` отмечен один пункт, пользователь выбирает «свой ответ» и отправляет текст из окна ввода
- **THEN** значение ответа в `answers` — этот текст без изменений, отметки в него не входят

### Requirement: Множественный выбор
В вопросе с `multiSelect` Enter на пункте MUST переключать отметку, ничего не отправляя; отдельная команда подтверждения MUST давать `allow` с ответом: метки отмеченных пунктов через запятую с пробелом в порядке пунктов; метка, содержащая запятую, MUST браться в двойные кавычки, как отвечает панель. Без отметок подтверждение MUST NOT отправляться.

#### Scenario: Две отметки
- **WHEN** отмечены `Cheese` и `Olives` в вопросе с тремя пунктами, пользователь подтверждает
- **THEN** значение ответа — `Cheese, Olives`

#### Scenario: Метка с запятой
- **WHEN** отмечены `Cheese, aged` и `Olives`, пользователь подтверждает
- **THEN** значение ответа — `"Cheese, aged", Olives`

#### Scenario: Подтверждение без отметок
- **WHEN** отметок нет, пользователь подтверждает
- **THEN** решение не отправлено, плагин сообщает, что ничего не отмечено

### Requirement: Несколько вопросов
Вопросы одного запроса MUST показываться по очереди; ответы накапливаются в плагине, итоговый экран показывает все ответы и ждёт подтверждения. Подтверждение MUST давать одно решение `allow` с ответами на все вопросы. С итогового экрана MUST быть возможен возврат к вопросу с сохранением ответов.

#### Scenario: Два вопроса
- **WHEN** пользователь ответил на оба вопроса и подтвердил итоговый экран
- **THEN** одно решение `allow`, в `answers` два ключа по текстам вопросов

#### Scenario: Возврат к вопросу
- **WHEN** на итоговом экране пользователь возвращается к первому вопросу
- **THEN** ответы сохранены, решение не отправлено

### Requirement: Отказ от вопроса
Буфер вопроса MUST давать те же отказы, что запрос разрешения: «отказать» — `deny`, «отказать с пояснением» — `deny` с `message`, «отказать и прервать» — `deny` с `interrupt: true`. Голое `allow` без `answers` MUST NOT отправляться.

#### Scenario: Отказ с пояснением
- **WHEN** пользователь отказывается от вопроса и вводит пояснение
- **THEN** решение — `deny` с `message` из окна ввода

### Requirement: Подтверждение плана
Буфер плана MUST показывать текст плана и действия: «подтвердить» — `allow` с `updatedInput`, равным исходному `tool_input`; «отказать с пояснением» — `deny` с `message` из окна ввода; «отказать» — `deny`; «отказать и прервать» — `deny` с `interrupt: true`. Режим после подтверждения MUST NOT выбираться плагином: его определяет Claude Code.

#### Scenario: Подтверждение
- **WHEN** пользователь подтверждает план
- **THEN** решение — `allow`, `updatedInput` равно исходному `tool_input`

#### Scenario: Правка плана
- **WHEN** пользователь отказывает с пояснением
- **THEN** решение — `deny` с `message` из окна ввода

### Requirement: Состояние после решения
После отправки решения буфер MUST показывать «решение отправлено» и MUST NOT позволять отправить второе. Когда в транскрипте появляется вложение `hook_permission_decision` с идентификатором вызова либо результат вызова, буфер MUST показать, что решение принято Claude Code.

#### Scenario: Решение принято
- **WHEN** решение отправлено, затем в транскрипте появляется вложение `hook_permission_decision` этого вызова
- **THEN** буфер показывает, что решение принято, повторная отправка недоступна

### Requirement: Диалог без запроса или нераспознанный
Для сессии без хука и для диалога, не приходящего через хук (например, доверие каталогу), плагин MUST сообщать, что агент ждёт ответа, и предлагать подключение с вводом через терминальный буфер (`node-view`). Плагин MUST NOT разбирать экран панели.

#### Scenario: Сессия без хука
- **WHEN** агент в `blocked`, а ждущего запроса у панели нет
- **THEN** плагин сообщает об ожидании и предлагает подключение с вводом, `pane.read` не вызывается

### Requirement: Сообщение об ожидании ответа
Когда у панели с открытым видом агент переходит в `blocked` и есть ждущий запрос, плагин MUST сообщить об ожидании и о команде открытия буфера диалога; окно и фокус MUST NOT меняться. Без ждущего запроса сообщение предлагает подключение с вводом.

#### Scenario: Запрос есть
- **WHEN** вид панели открыт, агент переходит в `blocked`, запрос принят
- **THEN** плагин сообщает о диалоге и команде открытия, окно и фокус прежние

### Requirement: Отсутствие таймеров и опроса
Приём соединений, сопоставление запросов, закрытие и ожидание решения MUST идти по событиям: соединения сокета, события herdr, дописывание транскрипта. Таймеры и опрос MUST NOT использоваться, в том числе для срока запроса.

#### Scenario: Тишина
- **WHEN** запрос открыт, ответа и событий нет
- **THEN** плагин не читает ни сокет, ни файлы и не ставит срока
