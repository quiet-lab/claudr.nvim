# herdr-client Specification

## Purpose
Клиент сокета API herdr: подключение, снимок, подписка на события, проверка протокола, недоступный и перезапущенный сервер.

## Requirements

### Requirement: Путь сокета
Клиент MUST подключаться к сокету API herdr по пути из `HERDR_SOCKET_PATH`, без этой переменной — по сокету herdr по умолчанию (`herdr.sock` в каталоге конфигурации herdr).

#### Scenario: Neovim запущен внутри панели herdr
- **WHEN** в окружении задан `HERDR_SOCKET_PATH`
- **THEN** клиент подключается по этому пути, а не по пути по умолчанию

#### Scenario: Neovim запущен вне herdr
- **WHEN** `HERDR_SOCKET_PATH` не задана
- **THEN** клиент подключается к сокету по умолчанию

### Requirement: Кадры и соответствие ответов
Клиент MUST обмениваться с сервером строками JSON, по одному объекту в строке. Запрос MUST иметь вид `{"id","method","params"}`, ответ — содержать `id` запроса и `result` либо `error`. Ответ с `error` MUST попадать вызвавшему как ошибка с кодом и текстом сервера. Несколько запросов MAY быть в полёте одновременно.

#### Scenario: Ответы приходят не по порядку
- **WHEN** клиент отправил два запроса подряд, а сервер ответил сначала на второй
- **THEN** каждый вызвавший получает ответ на свой запрос

#### Scenario: Ошибка сервера
- **WHEN** сервер отвечает `{"id":…,"error":{"code":"not_found","message":"pane not found"}}`
- **THEN** вызвавший получает ошибку с кодом `not_found` и текстом сервера

### Requirement: Идентификаторы — строки
Идентификаторы workspace, вкладок и панелей (например, `w1`, `w1:t1`, `w1:p1`) MUST обрабатываться как строки: числовой вид не гарантирован, в номерах бывают буквы. Клиент MUST NOT приводить их к числам.

#### Scenario: Идентификатор с буквой
- **WHEN** сервер присылает идентификатор панели, в котором есть буква
- **THEN** клиент хранит и передаёт его как строку без изменений

### Requirement: Проверка версии протокола
После подключения клиент MUST выполнить `ping`, ответ которого несёт версию протокола, и сравнить её с минимально поддерживаемой (22). Сервер с меньшим номером MUST отвергаться с сообщением, где названы найденный и требуемый номера; сервер с большим номером MUST приниматься, неизвестные поля ответов MUST игнорироваться.

#### Scenario: Старый сервер
- **WHEN** `ping` возвращает протокол 21
- **THEN** клиент не загружает дерево и сообщает, что требуется протокол 22 и новее, а найден 21

#### Scenario: Новый сервер
- **WHEN** `ping` возвращает протокол 23 и поля, которых клиент не знает
- **THEN** клиент работает, лишние поля игнорируются

### Requirement: Состав снимка
Клиент MUST читать `session.snapshot` и использовать из него workspace (`workspace_id`, `parent_workspace_id`, `label`, `number`, `agent_status`, `active_tab_id`), вкладки (`tab_id`, `workspace_id`, `label`, `number`) и панели (`pane_id`, `tab_id`, `workspace_id`, `foreground_process`, `cwd`, `agent`, `display_agent`, `agent_status`, `terminal_title`, `revision`, `agent_session`). Состояния агента, которые наблюдались: `unknown`, `idle`, `working`, `blocked`.

#### Scenario: Сессия агента
- **WHEN** у панели `agent_session` содержит `kind`, `agent` и `value`
- **THEN** клиент отдаёт `value` как идентификатор сессии Claude Code для панели с `agent = "claude"`

#### Scenario: Неизвестное состояние
- **WHEN** сервер присылает состояние агента, которого клиент не знает
- **THEN** клиент передаёт его как есть, ошибки нет

### Requirement: Снимок и подписка
Клиент MUST сначала открыть подписку `events.subscribe` на отдельном соединении и дождаться ответа `subscription_started`, затем запросить `session.snapshot` другим соединением. События MUST служить сигналом перечитать состояние: содержимое событий MUST NOT накладываться на снимок как данные. Перечитывания MUST выполняться по одному; событие, пришедшее во время чтения, MUST вызывать ещё одно.

#### Scenario: Событие во время чтения снимка
- **WHEN** во время выполнения `session.snapshot` приходит `pane_created`
- **THEN** после получения снимка клиент запрашивает снимок ещё раз, и итоговое состояние содержит новую панель

#### Scenario: Занятое соединение подписки
- **WHEN** подписка открыта и нужно выполнить запрос
- **THEN** запрос идёт другим соединением, соединение подписки остаётся занятым событиями

### Requirement: События жизненного цикла
Клиент MUST подписываться без параметров на события жизненного цикла workspace, вкладок и панелей (`workspace_*`, `tab_*`, `pane_created`, `pane_updated`, `pane_closed`, `pane_exited`, `pane_agent_detected`, `layout_updated`). Такие события приходят с видом через подчёркивание и полем `type` в данных; события подписки на панель — с видом через точку и без `type`. Клиент MUST принимать оба написания, определяя событие по полю `event`.

#### Scenario: Событие через подчёркивание
- **WHEN** приходит `{"event":"pane_closed","data":{"type":"pane_closed","pane_id":"w1:p2","workspace_id":"w1"}}`
- **THEN** клиент помечает кэш устаревшим и перечитывает состояние

#### Scenario: Событие подписки на панель
- **WHEN** приходит `{"event":"pane.agent_status_changed","data":{"agent_status":"working","pane_id":"w1:p1","workspace_id":"w1"}}` без поля `type`
- **THEN** клиент обрабатывает его так же, как событие с видом через подчёркивание, то есть по значению `event`

#### Scenario: Первое событие состояния без агента
- **WHEN** при запуске агента приходит `pane.agent_status_changed` с состоянием `unknown` и без поля `agent`
- **THEN** клиент принимает событие без ошибки

### Requirement: Выход процесса панели
Событие `pane_exited` MUST приниматься без кода выхода (в данных только `pane_id` и `workspace_id`). После `pane_exited` клиент MUST сверить состав с новым снимком и снять узлы, которых в снимке больше нет: когда процесс завершился в единственной панели workspace, панель и workspace исчезают без событий `pane_closed` и `workspace_closed`.

#### Scenario: Выход в единственной панели
- **WHEN** в единственной панели workspace завершается процесс, приходит `pane_updated` и `pane_exited`, а `pane_closed` и `workspace_closed` не приходят
- **THEN** клиент запрашивает снимок и снимает из дерева панель и workspace, которых в снимке нет

#### Scenario: Выход при остальных панелях
- **WHEN** приходит `pane_exited` для панели workspace, где есть другие панели
- **THEN** клиент перечитывает снимок, дерево соответствует снимку

### Requirement: Подписки по панелям
Подписки, привязанные к панели (`pane.output_changed`, `pane.agent_status_changed`), MUST создаваться только для панелей из последнего снимка. Одна неверная запись подписки отклоняет весь запрос, поэтому клиент MUST пересобирать подписки по событиям `pane_created`, `pane_closed` и `pane_exited` по новому снимку.

#### Scenario: Закрытие панели
- **WHEN** приходит `pane_closed` для панели с подпиской
- **THEN** клиент открывает подписку заново без этой панели, остальные подписки продолжают действовать

#### Scenario: Новая панель
- **WHEN** приходит `pane_created`
- **THEN** подписки включают новую панель после следующего снимка

### Requirement: Чтение панели
Клиент MUST читать вывод панели методом `pane.read` (`pane_id`, источник, формат); ответ несёт `text`, `revision` и `truncated`. Источник `recent_unwrapped` MUST применяться для видов, показывающих вывод целиком. Источник `recent` без числа строк отдаёт 80 строк, число строк ограничено 1000; источник `visible` отдаёт текущий экран. Формат `ansi` содержит управляющие последовательности оформления и перевод строки `\r\n`, формат `text` — чистый текст.

#### Scenario: Чтение вывода
- **WHEN** вид запрашивает вывод панели
- **THEN** клиент вызывает `pane.read` с источником `recent_unwrapped` и отдаёт `text` и `revision`

#### Scenario: Предел строк
- **WHEN** клиент запрашивает `recent` с числом строк 5000
- **THEN** ответ содержит не более 1000 строк, `truncated` равно `true`, клиент отдаёт их как есть

#### Scenario: Полноэкранная программа
- **WHEN** в панели работает полноэкранная программа
- **THEN** `visible`, `recent` и `recent_unwrapped` дают один и тот же текущий экран, клиент не считает это ошибкой

#### Scenario: Формат ansi
- **WHEN** клиент запрашивает формат `ansi` для цветного вывода
- **THEN** в `text` есть последовательности оформления вида `\x1b[38;5;1m`, а строки разделены `\r\n`

### Requirement: Потеря событий
Получив от сервера ошибку `events_lost`, клиент MUST считать кэш устаревшим, открыть новую подписку, дождаться `subscription_started`, запросить `session.snapshot` другим соединением и заменить кэш снимком.

#### Scenario: Отставший читатель
- **WHEN** сервер присылает `events_lost` и закрывает соединение подписки
- **THEN** клиент без вмешательства пользователя подписывается заново и обновляет дерево по новому снимку

### Requirement: Недоступный сервер
Если сервер недоступен (сокета нет или соединение отвергнуто), клиент MUST сообщить об этом состоянием «нет сервера», видимым подписчикам модели, и MUST NOT завершаться ошибкой при загрузке плагина. Действие, требующее сервера, MUST завершаться понятным сообщением.

#### Scenario: Запуск без сервера
- **WHEN** Neovim запущен, а сервера herdr нет
- **THEN** плагин загружается, дерево показывает состояние «нет сервера», команды запуска и сообщений сообщают, что сервер недоступен

### Requirement: Остановка сервера
Остановку сервера клиент MUST определять по закрытию соединения подписки без прощального кадра (конец потока без ошибки); подписка, поданная во время остановки, получает ошибку `server_unavailable` и закрытие. Оба случая MUST переводить клиента в состояние «нет сервера», кэш MUST считаться устаревшим.

#### Scenario: Остановка при открытой подписке
- **WHEN** соединение подписки закрывается без кадра
- **THEN** клиент переходит в состояние «нет сервера» и ждёт появления сокета

#### Scenario: Подписка во время остановки
- **WHEN** на запрос подписки приходит ошибка `server_unavailable`
- **THEN** клиент переходит в состояние «нет сервера», ошибка не показывается как сбой плагина

### Requirement: Перезапуск сервера
Готовностью нового сервера MUST считаться появление файла сокета API в его каталоге: клиент MUST отслеживать создание файла уведомлением файловой системы (`vim.uv.new_fs_event`), а не по расписанию. После появления файла клиент MUST выполнить проверку протокола, подписку и снимок заново; прежнее дерево MUST заменяться новым без перезапуска Neovim. Состояние, которое сервер восстановил из файла сессии, MUST читаться тем же снимком.

#### Scenario: Подмена сервера
- **WHEN** соединение рвётся и в каталоге сокета создаётся файл сокета API
- **THEN** клиент подключается, запрос снимка принимается сразу, дерево обновляется по новому снимку, подписки подаются заново

#### Scenario: Сервер запущен после Neovim
- **WHEN** Neovim работал без сервера и сервер herdr запускается
- **THEN** создание файла сокета вызывает подключение, дерево заполняется

#### Scenario: Сервер восстановил состояние
- **WHEN** после перезапуска сервер вернул прежние workspace и панели из файла сессии
- **THEN** дерево содержит их так, как показывает снимок; клиент не запускает агентов сам

### Requirement: Отсутствие таймеров и опроса
Клиент MUST NOT использовать таймеры, периодические проверки и повторные попытки по расписанию: переподключение, перечитывание и ожидание ответов идут по событиям (сокет, файловая система, выход процесса).

#### Scenario: Сервер недоступен длительное время
- **WHEN** сервера нет и сокета нет
- **THEN** клиент не выполняет ни одной попытки подключения, пока в каталоге сокета не произойдёт событие
