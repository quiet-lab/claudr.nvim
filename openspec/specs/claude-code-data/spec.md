# claude-code-data Specification

## Purpose
Чтение данных Claude Code одним модулем: транскрипты, субагенты, фоновые команды, слежение за файлами.

## Requirements

### Requirement: Единый модуль чтения данных Claude Code
Все данные Claude Code (транскрипты, `meta.json` субагентов, записи фоновых команд, файлы вывода) MUST читаться одним модулем. Остальной код MUST получать от него записи видов «субагент», «фоновая команда» и «реплика диалога» и MUST NOT разбирать эти форматы сам. Модуль дополнительно MUST разбирать вход хука `PermissionRequest` и вложение `hook_permission_decision` транскрипта (`agent-dialogs`).

#### Scenario: Изменение формата
- **WHEN** Claude Code меняет запись транскрипта
- **THEN** правка ограничивается модулем чтения, а дерево, виды и перечни получают те же виды записей

#### Scenario: Вход хука и вложение решения
- **WHEN** приходит вход хука `PermissionRequest` или в транскрипте появляется вложение `hook_permission_decision`
- **THEN** их разбирает модуль чтения, остальной код этих форматов не разбирает

### Requirement: Поиск транскрипта сессии
Транскрипт сессии MUST находиться по идентификатору сессии как файл `<идентификатор>.jsonl` в каталоге проекта среди каталогов `projects/` данных Claude Code. Каталог проекта MUST NOT выводиться из `cwd` панели: в сессии мог меняться рабочий каталог.

#### Scenario: Сессия сменила каталог
- **WHEN** `cwd` панели не совпадает с каталогом, по которому назван каталог проекта сессии
- **THEN** транскрипт находится по идентификатору среди всех каталогов проектов

#### Scenario: Транскрипта нет
- **WHEN** файла с таким идентификатором нет ни в одном каталоге проекта
- **THEN** модуль сообщает, что транскрипт не найден (ещё не создан), не возвращает записей и не считает это ошибкой

### Requirement: Ожидание транскрипта
Сессия с известным идентификатором, у которой транскрипта ещё нет (файл создаётся после первого сообщения), MUST ждать его создания: модуль MUST следить за каталогом `projects/` и каталогами проектов уведомлениями файловой системы и, когда появляется `<идентификатор>.jsonl`, начинать чтение. Отсутствие файла MUST NOT быть ошибкой.

#### Scenario: Первое сообщение сессии
- **WHEN** сессия известна, транскрипта нет, затем в каталоге проекта создаётся её файл
- **THEN** модуль по уведомлению начинает чтение и сообщает подписчикам записи

#### Scenario: Сессия без сообщений
- **WHEN** транскрипта нет и файл не создаётся
- **THEN** модуль не возвращает записей, не сообщает об ошибке и не читает файлы

### Requirement: Чтение транскрипта
Транскрипт MUST читаться как последовательность записей JSON, по одной в строке. Дописываемый транскрипт MUST читаться с запомненного смещения: уже прочитанные записи не разбираются повторно, незавершённая последняя строка ждёт завершения.

#### Scenario: Дописывание
- **WHEN** в транскрипт дописаны две записи после прочитанной части
- **THEN** модуль возвращает только эти две записи

#### Scenario: Недописанная строка
- **WHEN** последняя строка файла не закончена переводом строки
- **THEN** она не разбирается, пока не будет дописана

### Requirement: Реплики диалога
Модуль MUST выделять из транскрипта реплики пользователя и агента в порядке записи; каждая реплика несёт автора и текст. Служебные записи, не являющиеся репликами, в диалог MUST NOT входить.

#### Scenario: Диалог сессии
- **WHEN** в транскрипте записи пользователя, ответа агента и служебная запись
- **THEN** модуль возвращает две реплики в порядке записи

### Requirement: Субагенты сессии
Субагенты сессии MUST определяться по парам `agent-<id>.jsonl` и `agent-<id>.meta.json` в каталоге `subagents/` каталога сессии. Из `meta.json` модуль MUST читать `agentType`, `description`, `toolUseId`, `spawnDepth`, `parentAgentId`, `model` и `finished`; без `description` — брать описание из вызова `Agent` с идентификатором `toolUseId`. Задание субагента MUST быть первой непустой строкой первой записи транскрипта вида `user`. Посторонние файлы и подкаталоги MUST игнорироваться.

#### Scenario: Пара файлов
- **WHEN** в `subagents/` лежат `agent-a1.jsonl` и `agent-a1.meta.json`
- **THEN** модуль возвращает субагента `a1` с полями из `meta.json`

#### Scenario: Посторонний файл
- **WHEN** в `subagents/` лежит файл `agent-a1.forked-skill.json` или `agent-a1.forked-skill.marker.json`
- **THEN** он не даёт субагента

#### Scenario: Каталог workflow
- **WHEN** в `subagents/` есть каталог `workflows/` с вложенными каталогами и журналами
- **THEN** он игнорируется, субагентов не добавляет

#### Scenario: Описание из вызова и задание
- **WHEN** у субагента в `meta.json` нет `description`, `toolUseId` указывает на вызов `Agent` с описанием `D`, а первая запись транскрипта — запись пользователя с текстом `\n  Проверить ветку\n…`
- **THEN** модуль возвращает описание `D` и задание `Проверить ветку`

### Requirement: Вложенность субагентов
Субагенты всех уровней MUST лежать в одном каталоге `subagents/` сессии-владельца. Родитель MUST определяться полем `parentAgentId`; у субагента первого уровня поля нет.

#### Scenario: Вложенный субагент
- **WHEN** `meta.json` субагента B содержит `parentAgentId`, равный идентификатору субагента A
- **THEN** модуль возвращает B как дочернего субагента A, а A — как субагента первого уровня

### Requirement: Отметка завершения субагента
Субагент MUST считаться завершённым при `finished: true` в `meta.json`: это отметка только штатно завершённого. У работающего, остановленного и убитого вместе с родителем субагента поля `finished` нет; его отсутствие MUST читаться как «отметки завершения нет», а не как ошибка.

#### Scenario: Работающий субагент
- **WHEN** в `meta.json` нет поля `finished`
- **THEN** модуль возвращает субагента без отметки завершения

#### Scenario: Завершённый субагент
- **WHEN** в `meta.json` записано `finished: true`
- **THEN** модуль возвращает субагента с отметкой завершения

#### Scenario: Остановленный субагент без поля
- **WHEN** в `meta.json` остановленного субагента нет `finished`, последняя запись его транскрипта — реплика пользователя `[Request interrupted by user]`
- **THEN** модуль возвращает субагента без отметки завершения, остановку определяет следующее требование

### Requirement: Остановленный и фоновый субагент
Остановка фонового субагента MUST определяться по уведомлению `<task-notification>` со статусом `killed` и `task-id`, равным идентификатору субагента, в транскрипте родителя. Завершение фонового субагента — то же уведомление со статусом `completed`. Для субагента на переднем плане уведомлений нет, итог — результат вызова `Agent` в транскрипте родителя. Субагент, убитый вместе с родителем, остановленным не считается: его определяет состояние «оборван».

#### Scenario: Остановка субагента
- **WHEN** в транскрипте родителя уведомление с `task-id` субагента и статусом `killed`
- **THEN** субагент получает отметку завершения со статусом `killed`

#### Scenario: Субагент убит вместе с родителем
- **WHEN** у субагента нет `finished`, в транскрипте родителя нет уведомления о нём, а панель владельца закрыта
- **THEN** субагент получает состояние «оборван»

### Requirement: Запуск фоновой команды
Фоновой командой MUST считаться вызов инструмента Bash с `run_in_background: true` в транскрипте владельца (сессии или субагента). Из вызова модуль MUST брать `command` и `description`, из результата вызова — `backgroundTaskId` и путь файла вывода. Команда MUST принадлежать тому владельцу, в чьём транскрипте записан вызов.

#### Scenario: Команда субагента
- **WHEN** вызов с `run_in_background: true` записан в транскрипте субагента
- **THEN** модуль возвращает команду как принадлежащую этому субагенту

#### Scenario: Результат вызова
- **WHEN** в результате вызова есть `backgroundTaskId` и путь файла вывода
- **THEN** команда содержит идентификатор задачи и этот путь

### Requirement: Завершение фоновой команды
Завершением фоновой команды MUST считаться блок `<task-notification>` со `status` и `task-id` команды. Блок встречается в записях `queue-operation` (`enqueue`), `user` и `attachment` (`queued_command`, блок в поле `prompt`); модуль MUST распознавать все три и MUST NOT считать одно завершение дважды, сопоставляя по `task-id`. Статусы: `completed`, `failed` (код выхода — в `summary`), `killed`. Из блока читаются `task-id`, `tool-use-id`, `output-file`, `status`, код выхода.

#### Scenario: Команда завершилась
- **WHEN** в транскрипте появляется `<task-notification>` с `task-id` команды, `status` и кодом выхода 0 в `summary`
- **THEN** команда получает отметку завершения со статусом и кодом выхода 0

#### Scenario: Ненулевой код выхода
- **WHEN** уведомление имеет `status` `failed` и `summary` «… failed with exit code 3»
- **THEN** команда получает отметку завершения со статусом `failed` и кодом выхода 3

#### Scenario: Одно завершение в нескольких записях
- **WHEN** тот же блок записан как `queue-operation` и как `user`, либо как `attachment` и `queue-operation` с `remove`
- **THEN** команда получает одну отметку завершения

#### Scenario: Уведомление посреди хода
- **WHEN** блок записан вложением `queued_command`, а не записью `user`
- **THEN** модуль читает его так же, как запись `user`

#### Scenario: Чужое уведомление
- **WHEN** `task-id` уведомления не совпадает ни с одной известной командой
- **THEN** запись пропускается, ошибки нет

### Requirement: Остановка фоновой команды
Остановка команды инструментом остановки задач не оставляет блока `<task-notification>`. Остановка MUST определяться по результату вызова этого инструмента (`task_id` команды) в транскрипте владельца; команда получает отметку завершения со статусом `killed`.

#### Scenario: Команда остановлена
- **WHEN** в транскрипте владельца результат вызова инструмента остановки несёт `task_id` команды, а уведомления нет
- **THEN** команда получает отметку завершения со статусом `killed`

### Requirement: Команда, запущенная субагентом
Запись о запуске команды субагента MUST читаться из транскрипта субагента; уведомление о завершении лежит в транскрипте родительской сессии, а у субагента записано вложением. Модуль MUST находить завершение по `task-id` в обоих транскриптах, команда остаётся у субагента. Файл вывода лежит в каталоге сессии-владельца.

#### Scenario: Завершение команды субагента
- **WHEN** вызов записан в транскрипте субагента, а уведомление — в транскрипте родителя
- **THEN** команда принадлежит субагенту и получает отметку завершения по `task-id`

### Requirement: Задача наблюдения
Задачей наблюдения (`Monitor`) называется фоновая команда, чьи промежуточные уведомления приходят на каждую строку вывода без `status` и `tool-use-id`; итоговое — со `status` и `tool-use-id`. Модуль MUST считать завершением только уведомление со `status`; промежуточные MUST NOT завершать задачу.

#### Scenario: Промежуточное уведомление
- **WHEN** приходит `<task-notification>` с `task-id` задачи, с `<event>` и без `status`
- **THEN** задача остаётся работающей

#### Scenario: Итоговое уведомление
- **WHEN** приходит `<task-notification>` с `task-id` задачи и `status` `completed`
- **THEN** задача получает отметку завершения

### Requirement: Файл вывода фоновой команды
Файл вывода MUST создаваться при запуске команды, дописываться построчно и оставаться после конца сессии. Модуль MUST следить за ним уведомлениями файловой системы и читать с запомненного смещения. Файла может не оказаться (каталог временный): тогда доступны только статус и код выхода из записей транскрипта, отсутствие файла не ошибка.

#### Scenario: Дописывание вывода
- **WHEN** команда дописывает файл вывода
- **THEN** модуль по уведомлению отдаёт новые строки

#### Scenario: Файла нет
- **WHEN** команда завершена, а файла вывода нет
- **THEN** модуль отдаёт статус и код выхода, вывод помечен недоступным

### Requirement: Состояние «оборван»
Субагент или фоновая команда без отметки завершения MUST получать состояние «оборван», когда модулю сообщено, что панель владельца завершила процесс или закрыта. Правило общее для субагентов и команд, в том числе вложенных. Процесс владельца, убитый принудительно, не оставляет в транскрипте записей о своих командах: состояние определяется только этим правилом.

#### Scenario: Владелец упал
- **WHEN** у субагента нет отметки завершения и сообщено, что панель владельца закрыта
- **THEN** субагент и его фоновые команды без отметки завершения оборваны

#### Scenario: Владелец убит принудительно
- **WHEN** транскрипт владельца не содержит ни уведомления, ни результата остановки для команды, а сообщено, что процесс панели завершён
- **THEN** команда получает состояние «оборван»

#### Scenario: Владелец жив
- **WHEN** отметки завершения нет, а панель владельца жива
- **THEN** узел остаётся работающим

### Requirement: Слежение за изменениями
Изменения каталога сессии, `subagents/`, транскриптов и файлов вывода MUST отслеживаться уведомлениями файловой системы (`vim.uv.new_fs_event`). Пока каталога `subagents/` нет, MUST наблюдаться каталог сессии; когда `subagents/` создан, наблюдение MUST переходить на него.

#### Scenario: Первый субагент
- **WHEN** у сессии не было каталога `subagents/`, и он создаётся
- **THEN** наблюдение переходит на него, а подписчики получают нового субагента

### Requirement: Устойчивость к неизвестному
Неизвестные виды записей, неизвестные поля, непонятные значения известных полей, посторонние файлы и подкаталоги в каталогах субагентов и сессии MUST пропускаться без ошибки; повреждённая строка транскрипта MUST пропускаться, остальные записи читаться.

#### Scenario: Новое поле
- **WHEN** в `meta.json` или записи транскрипта есть поле, которого модуль не знает
- **THEN** поле игнорируется, остальные данные читаются

#### Scenario: Неизвестная запись
- **WHEN** в транскрипте запись неизвестного вида
- **THEN** она пропускается, чтение продолжается

### Requirement: Отсутствие таймеров и опроса
Модуль MUST NOT использовать таймеры и периодическое чтение: каждое чтение вызвано уведомлением файловой системы или запросом подписчика.

#### Scenario: Файлы не меняются
- **WHEN** уведомлений файловой системы нет
- **THEN** модуль не читает файлы
